<h1>Anthropic MHS: How AI Agents Now Control Physical Hardware</h1>

<p class="lede">Anthropic's Model Hardware Standard (MHS) is a shared specification that lets AI agents safely operate lab instruments, robotic arms, and factory equipment through MCP, CLI, and code files. Launched August 27, 2026 in research preview, it cuts hardware integration from weeks to hours and is model-agnostic -- no Claude lock-in required.</p>

<p>QuEra's quantum team went from 58% laser relock success to 99.3% overnight, unattended, using four Claude instances running through MHS. That's not a lab demo. That's a production system stabilizing quantum hardware autonomously. Whether you're building for biotech, manufacturing, or just watching where agents go next, here's what MHS actually is and what it means for builders.</p>

<h2>What is Anthropic's Model Hardware Standard?</h2>
<p>MHS is Anthropic's answer to a problem that anyone who's tried to connect AI to real hardware knows well: every device speaks a different language. MHS is a standardized driver spec that lets AI agents discover, operate, and chain commands across diverse hardware -- microscopes, liquid handlers, robotic arms, plate readers -- using simple read and write primitives. Think of it as MCP for the physical world.</p>
<p>Where the Model Context Protocol standardized how AI agents connect to software tools and data sources, MHS extends that philosophy to physical devices. Under the hood, it works through three mechanisms: MCP for structured agent communication, command-line interfaces, and code files that agents can generate and execute to run multi-step hardware sequences without reasoning at each step.</p>
<p>The key innovation is the device driver model. Instead of writing bespoke integration software for each instrument -- which typically takes a vendor weeks -- MHS lets developers document device characteristics in natural language tags. The driver converts those tags into reference files that an agent can read and act on. Carnegie Mellon's researchers got six incompatible instruments talking to each other in about eight hours, compared to the several weeks a vendor-built setup typically requires.</p>

<h2>Which devices does MHS actually support?</h2>
<p>As of August 2026, MHS supports any device with a programmable interface. The research preview has running integrations with lab instruments (microscopes, liquid handlers, plate readers, robotic arms), quantum computing hardware (laser systems, frequency controllers), and factory automation equipment. The standard is model-agnostic -- you're not locked into Claude.</p>
<p>The vendor lineup is substantial for a preview. Amazon Web Services is building MHS support into its Strands Robots library. Automata is adding it to the LINQ lab automation platform. Also committed: Danaher, Doosan Robotics, MBF Bioscience, QIAGEN's QIAsymphony Connect, Tecan's Fluent liquid handling platforms, Universal Robots, Hugging Face's LeRobot, and Raspberry Pi. That's 10 vendors building in before the spec is even open source.</p>
<p>Current access is waitlisted to scientific research labs and advanced manufacturers. The standard itself stays closed until the research preview concludes -- Anthropic hasn't announced an open source date yet, but open source is explicitly planned.</p>

<h2>What results are early partners actually seeing?</h2>
<p>The performance numbers from MHS partners are specific enough to quote directly. QuEra's laser relock success went from 58% to 99.3% across 700 blind trials, with recovery time dropping from 150 seconds to 6 seconds -- a 25x improvement. Carnegie Mellon reduced dose-response experiments to one-third the previous duration, with setup taking eight hours instead of the weeks a vendor-built integration typically requires. HHMI Janelia integrated a new camera in minutes instead of multi-day custom development. University of Washington connected six instruments in under a week.</p>
<p>Genentech's drug discovery setup illustrates the integration challenge: MHS let them automate BCA protein assay across a liquid handler, robotic arm, and plate reader -- three devices with fundamentally incompatible native interfaces -- with real-time error handling. That's the workflow that typically gets hand-coded over weeks by a vendor and breaks on every firmware update.</p>
<p>The QuEra result is the one I keep coming back to. Four Claude instances ran overnight, iterating on a decision-tree script that now handles laser recovery autonomously. The PID parameter tuning the agents generated also outperformed human expert parameters: residual noise dropped approximately 10x (from 15.7 mV to 1.55 mV), and the agent-tuned system held lock for a 19-hour continuous run without failure. Human-expert parameters averaged unlocking about 1.6 times per hour. An overnight agent run beat months of expert calibration.</p>

<h2>How to build with MHS today (and prepare for open source)</h2>
<p>If you have access to the research preview, the build flow is: write natural language tags describing your device's capabilities and safety limits, let the MHS driver convert those into a reference file, then point an agent at that reference file. From there, the agent chains read and write commands into code files for autonomous multi-step operation -- no reasoning at each step, just execution.</p>
<p>The multi-device orchestration pattern is where MHS gets interesting. Carnegie Mellon's setup involved a liquid handler, plate reader, robotic arm, and three monitoring cameras spread across three computers with incompatible native interfaces. MHS normalized all of them into a single agent-accessible surface. The agent didn't need to understand each device's native protocol -- it just needed the reference files.</p>
<p>If you're not in the preview yet, the practical move is to start mapping your hardware surface. Any device with USB, serial, Ethernet, or REST interfaces is a candidate. Document what read means for your device -- what state, what measurements -- and what write means: what commands it accepts, what its safety limits are. When open source drops, that documentation becomes your MHS driver with minimal rework.</p>
<p>One architectural pattern worth building around: MHS agents are designed for unattended operation and autonomous error recovery. Anthropic tested six safety conditions -- missing plate, rotated plate, reader busy, disconnected camera, unreachable device, active emergency stop -- and all six were automatically detected and halted without human intervention. If you're designing systems that currently assume human error-handling, MHS changes that assumption.</p>

<h2>What are the real limitations right now?</h2>
<p>Anthropic's announcement is honest about where the edges are. Claude's spatial and physical reasoning remains limited. Experts need to guide the agent on physical and chemical constraints -- recognizing that bubble formation in a liquid handler is a physical failure requiring a specific mitigation, not just a sensor error. That context has to live in your documentation, not the model's training data.</p>
<p>Non-programmable hardware is completely excluded. If your equipment doesn't have a programmable interface, MHS can't help. That excludes a meaningful share of legacy lab hardware.</p>
<p>Long-duration autonomous runs carry real compute costs. QuEra's overnight optimization was worth the cost (58% to 99.3%), but that math doesn't work for every workflow. Anthropic frames this as evaluate compute cost against researcher time saved -- the right frame, but it requires honest accounting.</p>
<p>The open source timeline is unknown. If you're planning a product that depends on MHS, don't build a launch dependency on it until Anthropic announces a date. Design for compatibility now, ship when the spec is public.</p>

<h2>FAQ</h2>
<h3>What is Anthropic's Model Hardware Standard (MHS)?</h3>
<p>MHS is a shared software specification that lets AI agents safely operate physical devices -- lab instruments, robotic arms, and factory equipment -- through standardized drivers. It uses MCP, CLI, and code files, and reduces hardware integration from weeks to hours. Launched August 27, 2026 in research preview to select labs and manufacturers.</p>

<h3>How is MHS different from MCP?</h3>
<p>MCP standardizes how AI agents connect to software tools, APIs, and data sources. MHS extends that same approach to physical hardware. MHS uses MCP as one of its three communication channels (alongside CLI and code files), but its core contribution is the standardized device driver layer that translates AI agent commands into machine-specific hardware controls.</p>

<h3>Which companies are already using MHS?</h3>
<p>Research preview partners include Genentech, Carnegie Mellon University, HHMI Janelia Research Campus, University of Washington, and QuEra Computing. Hardware vendors building MHS support include Amazon Web Services (Strands Robots), Automata, Danaher, Doosan Robotics, Universal Robots, Tecan, QIAGEN, Hugging Face (LeRobot), and Raspberry Pi.</p>

<h3>Is MHS open source?</h3>
<p>Not yet. Anthropic plans to open-source MHS after the research preview concludes. The preview is currently limited to a waitlist of scientific research labs and advanced manufacturers. No date has been announced for the open source release, but the commitment to open source is explicit in Anthropic's announcement.</p>

<h3>Can MHS work with any AI model, or only Claude?</h3>
<p>MHS is model-agnostic. Any AI model that can issue commands through MCP, CLI, or code files can work with MHS-compatible hardware. You're not required to use Claude -- the standard is designed so any device manufacturer and any model developer can adopt it.</p>
