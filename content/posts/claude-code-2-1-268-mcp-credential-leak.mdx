<h1>Claude Code 2.1.268: MCP Errors Were Leaking Credentials to Your Logs</h1>

<p class="lede">Claude Code v2.1.268, released September 10, 2026, patches a security issue where MCP and plugin error output was writing credentials and tokens into log files. It also fixes a regression from v2.1.265 that broke all third-party ANTHROPIC_BASE_URL endpoints with HTTP 400 errors, and adds a 300-second WebFetch timeout to prevent indefinite agent hangs.</p>

<p>Two of the fixes in this release are the kind that make you quietly nervous when you read the changelog. A credential leak in error logs -- the sort of thing that only fires when an MCP server throws, but logs that routinely ship to Datadog or CloudWatch with weaker access controls than your secrets vault. And a broken API endpoint that silently failed for several days before the fix landed. If you run MCP servers in production or route Claude Code through a custom gateway, here is what happened and what to audit.</p>

<h2>What was leaking, and why?</h2>
<p>MCP server errors and plugin errors in Claude Code were including credential data in their formatted error output -- API keys, OAuth tokens, and auth headers were surfacing in log entries generated during error paths. Normal operation with error-free MCP servers was not affected. Version 2.1.268 strips sensitive values from error formatting before they reach log output.</p>

<p>This fits a well-documented pattern in the MCP ecosystem. A <a href="https://www.practical-devsecops.com/mcp-security-statistics-2026-report/">2026 Practical DevSecOps report</a> found over 12,000 API keys and passwords exposed due to insecure MCP credential handling. Credential data leaking into logs is a specific variant of that exposure -- log files frequently ship to third-party aggregators (Datadog, Loki, CloudWatch, Splunk) without the same access controls as the secrets themselves. One compromised log stream exposes every key your MCP servers touch.</p>

<p>The attack surface is larger than it sounds. Claude Code connects to MCP servers for everything from file system access to custom API integrations. Production setups often connect to Slack, Notion, GitHub, Stripe, or internal APIs -- all of which use credentials that need fast rotation if exposed. If your MCP servers were erroring between v2.1.260 and v2.1.267, those error logs are worth auditing now.</p>

<h2>Who was broken by the HTTP 400 regression?</h2>
<p>Starting with v2.1.265, Claude Code introduced a regex pattern in the Artifact tool input schema that caused every API call to return HTTP 400 when routed through third-party Anthropic-compatible endpoints. Anyone pointing ANTHROPIC_BASE_URL at OpenRouter, LiteLLM, a custom proxy, or a corporate gateway was broken -- every turn failed -- from the v2.1.265 release date through September 10 when 2.1.268 shipped.</p>

<p>The root cause: the Artifact tool schema added a regex that the Anthropic API accepts but third-party endpoints (which parse tool schemas more strictly) reject with a 400. Claude Code sends this schema on every turn, so every turn failed. <a href="https://github.com/anthropics/claude-code/issues/46105">GitHub issue #46105</a> documents the reports and confirms the v2.1.265 breakage date. The fix in 2.1.268 removes the schema rejection by adjusting how the Artifact tool definition handles regex constraints when reaching non-Anthropic endpoints.</p>

<p>Worth noting: v2.1.265, v2.1.266, and v2.1.267 all shipped between September 4 and September 10 -- a six-day window where any ANTHROPIC_BASE_URL configuration was completely broken. Three releases shipped without catching a regression that broke all gateway users. That timeline matters if your team depends on OpenRouter or LiteLLM for cost management or model routing.</p>

<h2>WebFetch now has a 300-second hard timeout</h2>
<p>Claude Code's built-in WebFetch tool now enforces a 300-second (5-minute) hard timeout by default. Before 2.1.268, a hanging HTTP fetch stalled the entire agent session -- the subagent waited indefinitely with no recovery path, no error surfaced to the parent agent, and the only escape was killing the process and losing context. The 300-second default gives even slow servers enough runway while preventing runaway hangs from taking down long-running agents.</p>

<p>Set <code>CLAUDE_CODE_WEBFETCH_DEADLINE_MS</code> to override the default. Set it to <code>0</code> to disable entirely -- not recommended unless you have your own timeout handling downstream. <a href="https://github.com/anthropics/claude-code/issues/34565">GitHub issue #34565</a> documented the indefinite hang behavior as a long-standing request. For multi-agent workflows where a subagent WebFetch freeze cascades into a parent stall, this is one of the more impactful reliability fixes in recent releases.</p>

<h2>Gateway pricing parity and the gatewayInternalNetworks setting</h2>
<p>Two new additions ship together for teams running Claude Code through a self-hosted gateway. First, gateway pricing parity: when <code>pricing:</code> is configured in gateway.yaml, signed-in Claude Code clients receive the same rates through managed settings, so <code>/cost</code> and telemetry match the actual spend meter. Before this, cost estimates used Anthropic public rates regardless of your gateway pricing -- meaning tracked spend was wrong for any team using volume discounts or a reseller gateway.</p>

<p>Second, the new <code>gatewayInternalNetworks</code> managed setting lets administrators allow <code>/login</code> on the organization's own public IPv4 block. This is network-policy control for internal gateway authentication -- it enables auth flows without conflicting with existing CIDR access controls. Per the <a href="https://ccleaks.com/news/claude-code-2-1-268-sep-2026">2.1.268 technical changelog</a>, the setting also triggers startup warnings when <code>access_control.allow_cidrs</code> is empty and when requests arrive from public addresses -- giving operators early signals on misconfigured network policies.</p>

<h2>The rest of what shipped in 2.1.268</h2>
<p>Beyond the security and regression fixes, 2.1.268 ships several quality-of-life changes. Web-based Claude sessions now persist uploaded files for 24 hours instead of silently losing them after 6 hours -- a long-standing source of confusion when files disappeared mid-session with no warning. Plugin installation commands gained <code>--json</code> output for machine-readable responses, which matters for automated deployment scripts and CI pipelines that install plugins programmatically.</p>

<p>VS Code integration received fixes for session list loading with custom config directories and model pill display consistency. Claude Tag in Slack got per-public-channel memory isolation -- previous conversations in one channel were bleeding context into new ones, causing unexpected behavior in busy Slack workspaces. The update also resolves prompt caching and extended thinking breaking mid-session for SDK users via the <code>excludeDynamicSections</code> setting, which restores cache hits without interrupting extended thinking chains.</p>

<h2>How to check if your setup was exposed</h2>
<p>If you ran MCP servers in Claude Code on any version between v2.1.260 and v2.1.267, the audit is straightforward: check your log files for error entries that contain auth headers or token strings. Search for <code>Authorization:</code>, <code>Bearer</code>, or <code>x-api-key</code> appearing in error log entries. If your logs ship to a third-party aggregator, run the search there too -- that is where exposure becomes a real risk.</p>

<p>Steps to address this now: Update immediately with <code>npm install -g @anthropic-ai/claude-code@latest</code> and confirm with <code>claude --version</code>. On most systems, audit logs with <code>grep -i "bearer" ~/.claude/logs/*.log</code>. If you find credential data in error entries, rotate the credentials your MCP servers use -- static API keys are faster to rotate than OAuth tokens, so start there. For the HTTP 400 regression: if you were using ANTHROPIC_BASE_URL with a custom endpoint between September 6 and September 10, upgrading to 2.1.268 fully restores your setup with no gateway-side changes needed.</p>

<h2>FAQ</h2>
<h3>What exactly was leaking in the MCP credential bug in Claude Code?</h3>
<p>Claude Code was including credential data -- API keys, OAuth tokens, and auth headers -- in the error output generated when MCP servers or plugins threw errors. The leak only occurred in error paths, not during normal operation. If your MCP servers ran without errors during the affected versions (v2.1.260 to v2.1.267), you likely were not affected. Version 2.1.268 strips sensitive values from error formatting before they reach log output.</p>

<h3>Does this affect Claude Code on claude.ai, or only the local CLI?</h3>
<p>The MCP credential leak and the HTTP 400 regression both affect the locally installed <code>@anthropic-ai/claude-code</code> npm package. Claude.ai uses separate infrastructure that is not affected. The 24-hour file persistence fix and the Claude Tag in Slack memory isolation do affect the web and Slack experience. If you only use Claude.ai in a browser without running the CLI locally, the MCP credential issue does not apply to you.</p>

<h3>How do I update Claude Code to version 2.1.268?</h3>
<p>Run <code>npm install -g @anthropic-ai/claude-code@latest</code> in your terminal and confirm with <code>claude --version</code>. For enterprise gateway deployments, also update your gateway.yaml to apply the <code>gatewayInternalNetworks</code> and pricing parity settings -- these require explicit configuration to activate. Managed deployments that auto-update via CI or container rebuilds should already be on 2.1.268 if those pipelines ran after September 10, 2026.</p>

<h3>Was the credential leak exploited in the wild?</h3>
<p>No confirmed exploitation has been reported as of September 11, 2026. The exposure required an MCP server to throw an error during a session where credentials were active in memory. Setups where MCP servers ran cleanly without errors were not generating the vulnerable error output. If your MCP servers routinely errored during the affected window -- connection failures, auth failures during setup, misconfigured tools -- treat your logs as potentially containing credential data and rotate the affected credentials.</p>
