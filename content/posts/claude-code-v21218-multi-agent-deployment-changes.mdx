<h1>Claude Code v2.1.218: What Changed for Multi-Agent Deployments</h1>

<p class="lede">Claude Code v2.1.218 shipped July 22 with background execution for <code>/code-review</code>, a new "Needs input" state in agent view, and a Windows path corruption fix. Recent releases also hardened the permission boundary between parent agents and subagents, closing a Git redirection bypass that could steer a worktree-isolated subagent into the shared checkout.</p>

<p>I track every Claude Code release because the permission and isolation layer is where multi-agent workflows either hold together or fail in ways that are hard to debug. This release has one change that directly affects review-heavy production pipelines, and the surrounding permission hardening across recent releases is something anyone running parallel subagents should understand.</p>

<h2>What actually shipped in Claude Code v2.1.218?</h2>
<p>Claude Code v2.1.218 released July 22 with four main changes: <code>/code-review</code> now runs as a background subagent, agent view shows a "Needs input" state for stalled sessions, Windows paths with backslash-u-prefixed segments no longer corrupt into CJK characters, and the authentication status panel was retitled from "Cloud authentication" to "Authentication." No breaking changes in this release.</p>

<p>Here's the full change list:</p>
<ul>
<li><strong>New:</strong> <code>/code-review</code> now runs as a background subagent -- review work no longer fills your conversation context or blocks your main session</li>
<li><strong>New:</strong> Agent view shows sessions waiting on sandbox prompts, MCP-input requests, or managed-settings prompts as "Needs input" instead of "Working"</li>
<li><strong>Fixed:</strong> Windows paths containing backslash-u-prefixed segments were corrupted into CJK characters, making files inaccessible</li>
<li><strong>Fixed:</strong> Screen-reader announcements added for word and line deletions in <code>--ax-screen-reader</code> mode</li>
<li><strong>Changed:</strong> Authentication status panel retitled from "Cloud authentication" to "Authentication"</li>
</ul>

<p>Source: <a href="https://github.com/anthropics/claude-code/releases">github.com/anthropics/claude-code/releases</a>, <a href="https://releasebot.io/updates/anthropic/claude-code">Releasebot Claude Code changelog</a>.</p>

<h2>What background /code-review means for production pipelines</h2>
<p><code>/code-review</code> now runs as a background subagent rather than inline in your conversation. Triggering a code review no longer fills your context window or blocks you from continuing work -- the review runs in a dedicated subagent context, reports back when complete, and your main session continues uninterrupted.</p>

<p>Before this change, running <code>/code-review</code> in an active development session meant waiting for the review to finish before the conversation could continue. In short sessions that's fine. In long agentic workflows where you're building, committing, and iterating -- it was a blocking interrupt. Every review ate context and forced a pause.</p>

<p>Background execution changes the flow:</p>
<ol>
<li>Trigger <code>/code-review</code> at any point in your session</li>
<li>The review spins up as a background subagent with its own context window</li>
<li>Your main session continues -- build, test, write, commit</li>
<li>The review completes in the background and reports back as a task notification</li>
<li>Main context stays clean; review output lands separately in agent view</li>
</ol>

<p>For CI/CD pipelines using Claude Code as an automated reviewer, this matters even more. A pipeline stage that previously blocked waiting for review output can now fire-and-forget the review and continue downstream build steps, collecting results asynchronously. Claude Code is used by more than 115,000 active developers processing over 195 million lines of code per week -- a meaningful share of that is in automated pipelines where blocking calls are a genuine bottleneck. (<a href="https://www.aibuilderclub.com/blog/claude-code-worktree-parallel-agents">Source: AI Builder Club</a>, <a href="https://www.developersdigest.tech/blog/git-worktrees-claude-code-parallel-agents-guide">Developers Digest</a>)</p>

<h2>How the permission model works in multi-agent Claude Code</h2>
<p>Each Claude Code subagent gets its own context window, tool access list, and permission mode. The parent session's permission settings take precedence -- if the parent runs in <code>bypassPermissions</code> mode, subagents cannot override that. Subagents also cannot exceed the parent's tool access scope, making the parent the effective permission ceiling for the entire agent tree.</p>

<p>The key permission fields that govern subagent behavior:</p>

<ul>
<li><strong>permissionMode:</strong> Controls how the subagent handles approval prompts. Options are <code>default</code> (prompts user for each action), <code>acceptEdits</code> (auto-accepts file edits but prompts for other actions), and <code>bypassPermissions</code> (skips all prompts). Parent's <code>bypassPermissions</code> takes precedence over any subagent <code>permissionMode</code>.</li>
<li><strong>Tool access inheritance:</strong> A subagent can only use tools the parent session has access to. You can restrict subagents to a subset of the parent's tools, but you cannot grant a subagent tools the parent doesn't have.</li>
<li><strong>CLAUDE_CODE_SUBAGENT_MODEL:</strong> Environment variable that routes all subagents to a specific model. Useful when you want orchestrator and workers on different model tiers -- for example, Opus 4.8 for the orchestrator and Haiku 4.5 for bulk processing workers.</li>
</ul>

<p>In practice, the permission model means you design security at the orchestrator level. A subagent can't grant itself more access than the parent authorized. What you do need to watch is <code>bypassPermissions</code> at the parent level -- if the orchestrator runs with permissions bypassed, every child agent in the tree also runs without prompts. That's often desirable in automated pipelines and risky in anything that processes external content.</p>

<p>When background agents resume after a stop, they now restore their original tool restrictions and permission mode instead of reverting to defaults -- a fix that landed in the recent release train and prevents a subtle permission expansion bug where a resumed agent could silently gain broader access than it originally had. Source: <a href="https://code.claude.com/docs/en/permissions">Claude Code official permissions documentation</a>.</p>

<h2>The Git worktree bypass that got patched in recent releases</h2>
<p>Recent Claude Code releases blocked Git redirection vectors from steering worktree-isolated subagents into the shared checkout. The vectors blocked include <code>-C</code>, <code>--git-dir</code>, <code>GIT_DIR</code>, and <code>GIT_WORK_TREE</code> -- flags a subagent processing malicious content could use to escape its isolated worktree. The fix applies at the Bash tool layer before any Git command executes.</p>

<p>Worktree isolation is the mechanism that makes parallel subagents safe in the first place. When you spawn a subagent with <code>isolation: "worktree"</code>, Claude Code creates a fresh git worktree for that agent to work in, separate from the main checkout. Changes in the worktree don't affect the main branch until explicitly merged. Two agents can edit different parts of the codebase simultaneously without interfering. The worktree is auto-cleaned if the subagent made no changes.</p>

<p>The storage overhead to plan for: a 2GB repository with 5 active worktrees requires roughly 10GB or more of disk space. The <code>.git</code> object database is shared, but every working tree's files are duplicated. (<a href="https://claudefa.st/blog/guide/development/worktree-guide">Source: claudefa.st worktree guide</a>)</p>

<p>The bypass the patch closes is subtle. Git has built-in flags that redirect which directory and repository it operates on: <code>-C /other/path</code> changes Git's working directory before running, <code>--git-dir=/path/to/git</code> overrides the git database location, and the environment variables <code>GIT_DIR</code> and <code>GIT_WORK_TREE</code> do the same. A worktree-isolated subagent could be instructed -- via malicious document content, MCP tool output, or user input -- to include one of these flags in a Git command, effectively stepping out of its worktree and operating on the shared main checkout. The fix blocks all four at the Bash tool layer so the subagent can't pass them regardless of instruction source.</p>

<p>If your agentic pipeline processes external content -- user-provided documents, web-fetched data, MCP tool responses from external services -- understand what worktree isolation does and doesn't protect against. It isolates file edits. It does not isolate architecture decisions, API contracts, or test coverage. The Git redirection fix closes a specific escape vector; broader prompt injection from external content is still a design-level concern.</p>

<h2>Understanding the "Needs input" state in agent view</h2>
<p>Agent view in v2.1.218 now shows sessions waiting on a sandbox prompt, MCP input request, or managed-settings prompt as "Needs input" instead of "Working." This distinction matters for production pipelines: a "Needs input" session is stalled waiting for operator response, not making progress. "Working" means the agent is actively running.</p>

<p>Before this change, both states displayed as "Working" -- meaning you couldn't tell from the agent view whether a long-running session was productively processing or silently blocked on a prompt that would never be answered. For an overnight batch run, that's the difference between finding results in the morning and finding a session that stalled at 2am and sat idle for 6 hours.</p>

<p>What triggers "Needs input":</p>
<ul>
<li><strong>Sandbox permission prompts:</strong> The agent tried to run a Bash command and hit a permission gate -- it's waiting for you to approve or deny before it can continue</li>
<li><strong>MCP-input requests:</strong> An MCP tool the agent called is awaiting user input -- common in interactive MCP servers that prompt for confirmation before taking action</li>
<li><strong>Managed-settings prompts:</strong> An organizational policy constraint requires human approval before the agent proceeds to the next action</li>
</ul>

<p>For fully automated production pipelines, the fix is to configure <code>permissionMode: "bypassPermissions"</code> if you trust the pipeline's scope, or set up monitoring that alerts when any session enters "Needs input" state. Discovering a blocked session 8 hours after it stalled is how you get unreliable automation and missed SLAs.</p>

<h2>Updating and what to check</h2>
<p>Updating to v2.1.218 requires a single npm command -- no config changes needed unless you want to leverage the new permission controls or background review behavior. The background <code>/code-review</code> feature activates automatically; the "Needs input" state appears in agent view without configuration; the Git redirection fix is active by default.</p>

<p>Update via npm:</p>
<pre><code>npm update -g @anthropic-ai/claude-code</code></pre>

<p>Confirm your version:</p>
<pre><code>claude --version</code></pre>

<p>If you run Claude Code in Docker images or pin versions in CI/CD pipelines, update the pin to <code>2.1.218</code>. If you've been hitting file access issues on Windows with unusual path characters, the CJK corruption fix resolves that class of issue. If you run parallel subagents in worktrees, the Git redirection fix is already active from the recent release train.</p>

<h2>FAQ</h2>

<h3>What does background /code-review do in Claude Code v2.1.218?</h3>
<p>In v2.1.218, <code>/code-review</code> runs as a background subagent with its own context window instead of executing inline in your main session. Triggering a code review no longer blocks your conversation or fills your context. The review processes independently and reports back as a task notification, letting your main session continue writing, building, or testing without interruption.</p>

<h3>What is the "Needs input" state in Claude Code agent view?</h3>
<p>Added in v2.1.218, "Needs input" appears in agent view when a session is stalled waiting for operator response -- on sandbox permission prompts, MCP tool input requests, or managed-settings approval gates. Previously these sessions displayed as "Working," making it impossible to tell from the dashboard which sessions were actively processing versus blocked and waiting for action.</p>

<h3>How do subagent permissions work in Claude Code multi-agent setups?</h3>
<p>Claude Code subagents inherit the parent session's permission ceiling. If the parent runs with <code>bypassPermissions</code>, all child subagents also bypass approval prompts. Subagents cannot grant themselves tools the parent doesn't have. You can restrict a subagent to a subset of the parent's tools via its agent definition, but you cannot expand its access beyond what the parent session allows.</p>

<h3>What was the Git redirection bypass in Claude Code worktrees?</h3>
<p>Worktree-isolated subagents could previously escape their isolated worktree by passing Git redirection flags -- <code>-C</code>, <code>--git-dir</code>, <code>GIT_DIR</code>, or <code>GIT_WORK_TREE</code> -- in Bash commands. A subagent processing malicious content could use these to operate on the shared main checkout instead of its isolated worktree. The fix blocks all four vectors at the Bash tool layer automatically.</p>
