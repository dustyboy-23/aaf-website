<h1>MCP 2026-07-28: What Breaks and How to Migrate Your Server</h1>

<p class="lede">The MCP 2026-07-28 spec is the biggest protocol change since MCP launched. It removes the initialize handshake, drops session IDs, deprecates Roots, Sampling, and Logging, and adds MRTR, MCP Apps, and a formal Tasks extension. Old servers that rely on session state will break. Here is the exact migration path.</p>

<p>I have been tracking the MCP spec since the release candidate dropped in early July. If you have MCP servers in production, the July 28 final spec requires real changes -- not just version bumps. Here is what I found running through the breaking changes and the official migration docs.</p>

<h2>What exactly changed in the MCP 2026-07-28 spec?</h2>

<p>The 2026-07-28 MCP spec removes the session layer entirely. The initialize/initialized handshake is gone. The Mcp-Session-Id header is gone. Every request is now self-describing -- it carries the protocol version and client identity in <code>_meta</code>. This turns MCP servers into stateless HTTP services that can sit behind a plain round-robin load balancer without shared storage or sticky sessions.</p>

<p>This is the most substantive MCP change since authorization support was added. Before July 28, MCP assumed a single stateful connection between client and server. The session handshake was mandatory. Any server handling multiple clients needed careful session tracking. That entire model is replaced with a stateless core where any instance can serve any request.</p>

<p>Three new required headers do the routing work that sessions previously handled: <code>Mcp-Method</code> (the operation name), <code>Mcp-Name</code> (the server name), and the W3C <code>traceparent</code>. Gateways and firewalls can now inspect MCP traffic without parsing JSON bodies -- a major operational improvement. Cloudflare already uses a variant of this approach: their Code Mode MCP Server scaled to thousands of requests per second and served billions of tool calls since February 2026 (<a href="https://blog.cloudflare.com/mcp-v2/">Cloudflare blog</a>).</p>

<p>The official Tier 1 SDKs -- TypeScript, Python, Go, and C# -- have all shipped updates for the 2026-07-28 spec. Rust is in beta. For context on why this spec change matters at scale: the TypeScript and Python SDKs each surpassed 1 billion total downloads, and all Tier 1 SDKs collectively reach around 500 million monthly downloads (<a href="https://blog.modelcontextprotocol.io/posts/2026-07-28/">MCP blog</a>). That is a large footprint for a breaking change.</p>

<h2>What breaks? The three categories of breakage</h2>

<p>Breaking changes in the 2026-07-28 spec fall into three buckets: session state that the protocol no longer carries, deprecated features that stop receiving new capabilities, and transport deprecations that will strand some existing clients as the ecosystem moves on. A 12-month deprecation window means nothing is immediately removed -- but the clock is running on everything in this list.</p>

<p><strong>Session-dependent state</strong></p>

<p>The most impactful break. If your server stores any data scoped to an <code>Mcp-Session-Id</code> -- user preferences, in-flight context, accumulated tool results -- that state now needs to live somewhere else. The spec moves session context to a client-held opaque handle. Your server instance is expected to be stateless; external stores (Redis, a database, the client payload itself) now own any per-session data.</p>

<p>Servers that used <code>initialize</code> to negotiate capabilities also break. The capability negotiation model is removed from the protocol layer entirely. Feature detection happens through other mechanisms in the new spec.</p>

<p><strong>Deprecated: Roots, Sampling, and Logging</strong></p>

<p>Three features moved from core to deprecated status. They still work -- the deprecation policy guarantees a minimum 12-month window from the deprecating revision before anything becomes eligible for removal, per the <a href="https://modelcontextprotocol.io/specification/2026-07-28/changelog">official changelog</a>. But new implementations should not adopt them, and existing implementations should migrate while the window is open.</p>

<p>The migration paths are direct: replace Roots with directory or file parameters in tool calls or server configuration; replace Sampling by calling LLM provider APIs directly; replace Logging with stderr output (stdio servers) or OpenTelemetry.</p>

<p><strong>Transport deprecation</strong></p>

<p>Legacy HTTP+SSE transport is deprecated with the same 12-month minimum window. Old clients that only speak legacy HTTP+SSE will not be able to connect to new servers that have dropped it. The transition window exists so you can run both transport paths simultaneously while the ecosystem moves forward.</p>

<p>Dynamic Client Registration (DCR) is also deprecated, replaced by Client ID Metadata Documents (CIMD). The auth model received a broader hardening pass: RFC 9207 issuer validation is now required before code redemption, and client credentials are bound to the issuing authorization server.</p>

<h2>How do you migrate your MCP server to the 2026-07-28 spec?</h2>

<p>Migrating to the 2026-07-28 spec has four concrete steps: remove the initialize handshake, externalize any session state, add the three required headers, and update or remove deprecated features. If you are on a Tier 1 SDK, version updates handle most of the low-level protocol changes. Custom servers need to handle each piece manually.</p>

<p><strong>Step 1: Remove the initialize handshake</strong></p>

<p>Stop handling <code>initialize</code> requests as the mandatory first message. The new spec sends protocol version and client identity in <code>_meta</code> on every request. Update your request parsing to read from there instead of from accumulated session state.</p>

<pre><code class="language-javascript">// Before: session-scoped initialization
server.on('initialize', (req) => &#123;
  sessions[req.sessionId] = &#123; clientInfo: req.params, tools: [] &#125;
&#125;)

// After: read from _meta on each request
const clientVersion = req._meta?.protocolVersion
const clientInfo = req._meta?.clientInfo
</code></pre>

<p><strong>Step 2: Externalize session state</strong></p>

<p>Anything your server stores by session ID needs a new home. For simple use cases, the client can carry state as an opaque token in each request. For complex cases -- long-running agent sessions, accumulated tool results -- use an external store. Redis works. A database works. The hard constraint: your server instance must handle any request without local state from prior requests on the same connection.</p>

<p><strong>Step 3: Add the three required headers</strong></p>

<p>Your server needs to emit -- and clients need to send -- <code>Mcp-Method</code>, <code>Mcp-Name</code>, and <code>traceparent</code> on every request. If you are behind a gateway or running in a serverless environment, these headers enable routing and observability without JSON body inspection. This is what makes MCP traffic behave like any standard HTTP API for your infrastructure layer.</p>

<p><strong>Step 4: Update or remove deprecated features</strong></p>

<p>Roots: replace with explicit parameters or server configuration. Sampling: call your LLM API directly. Logging: switch to stderr or OpenTelemetry. Legacy HTTP+SSE: keep running for existing clients while you add the new transport path for new clients. Do not remove legacy support before your client population has migrated.</p>

<p>If you are on the TypeScript or Python SDK, start with the version update -- the Tier 1 SDKs ship migration helpers that handle header negotiation and <code>_meta</code> parsing. The <code>createMcpHandler</code> API simplifies the transition considerably. Run your test suite after the update; failing tests surface your session-state dependencies more precisely than manual auditing.</p>

<h2>What is new in the spec that is actually worth using?</h2>

<p>The 2026-07-28 spec is not only removals. Multi Round-Trip Requests (MRTR), MCP Apps, the official Tasks extension, and cacheable list results add real capabilities -- all designed for the stateless model. If you are rebuilding your server for the new spec, these are the features worth understanding now rather than discovering later.</p>

<p><strong>MRTR: server-initiated input without a held-open stream</strong></p>

<p>Multi Round-Trip Requests replace the old elicitation pattern. Previously, getting user input mid-call required a held-open stream -- impossible in a stateless model. MRTR fixes this: the server returns an <code>input_required</code> result, the client collects the needed information, and the client retries with it. No persistent connection needed. This enables clarification questions, confirmation dialogs, and multi-step forms inside tool calls without abandoning the stateless architecture.</p>

<p><strong>MCP Apps: HTML in a sandboxed iframe</strong></p>

<p>MCP Apps are server-rendered HTML interfaces that run in a sandboxed iframe inside the client. Tools declare their UI templates upfront, so clients can prefetch and security-review them before rendering. UI actions -- button clicks, form submissions -- flow back through the same JSON-RPC channel as regular tool calls. No separate WebSocket or iframe message protocol required.</p>

<p>The official ext-apps repository has working examples across multiple categories: 3D visualizations (threejs-server), data exploration (cohort-heatmap-server, wiki-explorer-server), business tools (scenario-modeler-server, budget-allocator-server), and utilities (qr-server, transcript-server). If your tools currently return long JSON blobs or markdown tables that clients render awkwardly, MCP Apps is the intended path forward (<a href="https://modelcontextprotocol.io/extensions/apps/overview">MCP Apps docs</a>).</p>

<p><strong>Tasks extension: stateless long-running operations</strong></p>

<p>Tasks moved from experimental core to an official extension after production use drove a redesign. The new lifecycle fits the stateless model: <code>tools/call</code> returns a task handle, and the client drives progress by polling with <code>tasks/get</code>, updating with <code>tasks/update</code>, or canceling with <code>tasks/cancel</code>. No subscription model, no held-open stream. If you are building agents that run operations over minutes -- code execution, file processing, multi-step pipelines -- the Tasks extension is the right primitive now.</p>

<p><strong>Cacheable list results</strong></p>

<p>Tools/list, prompts/list, resources/list, and resources/read now include <code>ttlMs</code> and <code>cacheScope</code> parameters. Return a reasonable TTL on your capability lists and clients skip the re-fetch overhead on every request. For high-traffic servers, this is one of the fastest performance wins available in the new spec -- add a few fields to your existing list responses and you are done.</p>

<h2>When should you migrate, and in what order?</h2>

<p>The 12-month deprecation window means deprecated features are eligible for removal starting in July 2027 -- but eligible is not the same as immediately removed. The practical timeline for legacy HTTP+SSE disappearing is probably 18-24 months from now. That said, building new functionality on top of deprecated primitives means paying double migration cost later. Here is the priority order I would use.</p>

<p><strong>Immediate:</strong> Update your Tier 1 SDK to the 2026-07-28 version and add the three required headers. This is the minimum needed to maintain compatibility with new clients without breaking old ones. On a Tier 1 SDK, this is an afternoon of work.</p>

<p><strong>Next sprint:</strong> Remove the initialize handshake and externalize session state. This is the architecturally significant change. Once done, your server can deploy to serverless infrastructure -- Cloudflare Workers, AWS Lambda, any platform -- without complexity around sticky sessions or shared state stores at the protocol layer. Stateless deployment is the main operational win of this spec change and it compounds over time as your deployment footprint grows.</p>

<p><strong>Before year-end:</strong> Migrate away from Roots, Sampling, and Logging. These still work, but shipping new features against deprecated primitives is a mistake. Start new functionality on the replacement patterns now so you are not doing two migrations later.</p>

<p>David Cramer, co-founder of Sentry, put it plainly after deploying to production before the spec was finalized: "This new spec cleans up a bunch of the nonsense around auth and tools." Sentry was willing to take the pre-release risk, which signals how stable the spec was well before July 28. If your production risk tolerance is lower than Sentry's, the final spec is that much more justification to move now.</p>

<h2>FAQ</h2>

<h3>Do my existing MCP servers break immediately after July 28, 2026?</h3>
<p>No -- existing MCP servers do not break immediately. The 12-month deprecation window means Roots, Sampling, Logging, legacy HTTP+SSE, and DCR all remain functional until at least July 2027. However, servers using the initialize handshake and Mcp-Session-Id become incompatible with new clients that only speak the 2026-07-28 spec unless you add a backward-compatibility layer. The real risk is not breakage today -- it is client ecosystem drift over the next 6-12 months as new clients stop supporting the old protocol path.</p>

<h3>What is the simplest way to check if my server needs migration work?</h3>
<p>Run four checks: Does your server require an initialize handshake before accepting other requests? Does it track per-session state keyed to Mcp-Session-Id? Does it use Roots, Sampling, or Logging? Does it use legacy HTTP+SSE transport? If you answered yes to any of these, you have migration work ahead. If you are on a Tier 1 SDK (TypeScript, Python, Go, C#), update the package and run your tests first -- the SDK handles lower-level protocol changes, and failing tests surface your session-state dependencies precisely.</p>

<h3>How does MRTR replace the old elicitation model?</h3>
<p>In the old model, getting user input mid-call required a held-open connection: the server sent a request back over the active stream, and the client responded on that same stream. In the stateless model, that is impossible. MRTR uses a polling pattern instead: the server returns an input_required result with a handle, the client collects the information from the user, and the client retries the original call with the collected data attached. The server holds nothing open. Any stateless instance can process the retry without knowledge of what came before.</p>

<h3>Should I implement MCP Apps now?</h3>
<p>Worth evaluating now if your tools produce output that benefits from visual representation -- dashboards, data tables, maps, forms, confirmation dialogs. The sandboxed iframe model is well-specified and the official ext-apps repository has working examples you can run today. If your tools return long JSON strings or markdown tables that clients render awkwardly, MCP Apps gives you server-controlled rendering without requiring client-side code changes. All UI actions flow through the existing JSON-RPC channel, so there is no new security surface to audit on the client side.</p>
